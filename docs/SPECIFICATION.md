## 1. Назначение и границы этапа

Приложение помогает ученику начальной школы замечать, куда уходит время, выстраивать регулярные привычки и оставлять место для отдыха. Личный сказочный мир развивается за заработанные звёзды. Главный принцип: **качество занятий и устойчивость привычек важнее рекордов скорости**.

В текущем этапе поставляются спецификация и интерактивный HTML/CSS/JS-макет. Backend, настоящая авторизация, Supabase, AI, серверные начисления и production Docker будут следующим этапом. Локальные данные макета не являются защищённым аккаунтом. Графики времени используют демо-записи и внесённые пользователем изменения; достижения, проценты и пример письма явно иллюстративны.

### Зафиксированные требования
- Пять обязательных предметов: Математика, Русский язык, Литературное чтение, Окружающий мир, Английский язык.
- Прогулки с начальной целью 120 минут в день; внеклассное чтение и произвольные занятия.
- Два типа задач: измерение времени и отметка выполнения.
- Независимые таймеры; пауза, продолжение, сохранение и сброс; ручной ввод за прошлые даты.
- Поручения с расписанием и без него, отметки на главной.
- Личные статистика, достижения, кошелёк и игровой мир для каждого пользователя.
- Светлая, тёмная и системная тема; адаптивные desktop/tablet/mobile, обе ориентации.
- Python backend, внешняя реляционная БД Supabase, один контейнер frontend + backend.

### Предлагаемые решения, требующие согласования
1. Название валюты — **звёзды**, игровой мир — **Острова открытий**.
2. Взрослый подтверждает качество домашнего задания; без подтверждения сокращение времени не приносит награду.
3. Начисление каждые семь дней, хотя предварительная оценка скользящего окна обновляется ежедневно.
4. Редкие добровольные дела можно награждать сразу, но это отдельная отключаемая политика с лимитами.
5. AI не получает права произвольно создавать валюту: сервер ограничивает результат допустимыми условиями и суммой.
6. Первоначально один аккаунт соответствует одному ребёнку; взрослый может управлять несколькими связанными профилями.

## 2. Роли и доступ

| Роль | Возможности |
|---|---|
| Ученик | Свои таймеры и записи, отметки поручений, статистика, покупки в мире, тема |
| Родитель | Связанные дети, расписания, цели, подтверждение качества, исправление данных, политика наград |
| Администратор установки | Подключения, секреты, обслуживание; отдельная усиленная проверка доступа |

Смена профиля в интерфейсе не заменяет авторизацию. Каждый запрос проверяет права на сервере. Ребёнок не меняет тарифы наград, роль, баланс, API-ключи или подключения. Разовый PIN может служить удобством интерфейса, но не самостоятельной защитой административных API.

## 3. Информационная архитектура и экраны

### 3.1 Вход и первый запуск (следующий этап)
- Вход, выход, восстановление доступа. Регистрация взрослым и создание связанного профиля ребёнка.
- Первичная настройка установки по одноразовому bootstrap-токену, заданному при запуске контейнера. После создания администратора bootstrap отключается.
- Выбор имени, часового пояса IANA, расписания уроков, цели прогулки и стартовых обязанностей.
- Не просить ребёнка вводить реальные внешние API-ключи.

### 3.2 Мой день
Порядок приоритета: приветствие → мир и ближайшая цель → сегодняшние показатели → поручения и занятия → недельные графики → достижения.

Компоненты:
- Имя и userpic Алексея, дата в его часовом поясе, баланс звёзд.
- Карточка мира с иллюстрацией, прогрессом до следующей покупки и переходом в игру.
- Краткие показатели: подтверждённое изменение времени уроков, прогулка сегодня / 120 минут, выполненные дела / запланированные.
- Список сегодняшних поручений с доступными checkbox, расписанием и состоянием. Добровольные дела выделяются и не ухудшают обязательный процент.
- Предметы и занятия: название, состояние таймера, несохранённое время, переход на карточку. Ненулевой таймер виден даже после смены страницы.
- **Stacked bar chart:** один столбец на календарную неделю (понедельник–воскресенье), Y — минуты, X — начало недели; слои уроки / прогулки / другие занятия. Переключение на предметы, фильтр 4/8/12 недель. Текущая неполная неделя помечена; её нельзя прямо сравнивать с полной без пояснения.
- **Pie/donut:** распределение учтённого времени за выбранный период. Процент и минуты по категориям, общий итог. Не изображать долю от всех 24 часов.
- Достижения, предварительный результат текущего окна и дата следующего начисления. Нулевой результат объяснять нейтрально.

### 3.3 Уроки / другие занятия / прогулка
Каталог предметов и пользовательских занятий. Для прогулки отдельный пункт меню; пользовательские timed-занятия доступны в каталоге с группой «Другие занятия».

Карточка занятия:
- Название, назад, переход к другому предмету.
- Таймер HH:MM:SS; «Начать/Продолжить», «Пауза», «Сохранить», «Сбросить».
- Сохранение фиксирует накопленное время в запись и обнуляет только этот таймер.
- Ручная форма: дата, часы/минуты (в макете минуты), необязательная заметка, объём и сложность домашнего задания.
- Line chart **за всё время**, без ограничения последними 7 днями: X — календарные даты, Y — сумма минут за дату. Только дни с данными, в хронологическом порядке; все соседние точки последовательно соединены, даже если между ними дни/месяцы без занятий. Дни без записей не превращаются в нули. Несколько записей за одну дату агрегируются. Сокращаться может только число подписей оси, не число точек.
- Полная история **за всё время**: дата, длительность, источник, подтверждение качества, комментарий, редактировать/удалить (с журналом изменений). Таблица содержит все записи, включая внесённые вручную за давние даты.
- Для прогулки: дневная цель, накопленное время и оставшееся время; превышение цели не умножает награду.
- Состояния: пустая история, загрузка, ошибка, таймер идёт, пауза, сохранение, конфликт версии.

### 3.4 Поручения
Сегодня / неделя / все. Добавление, архивирование, порядок, расписание. Ежедневно, будни, выбранные дни недели, раз в неделю в конкретный день; дата начала и необязательная дата окончания. Исключения: отпуск, болезнь, заранее согласованный пропуск. Изменение расписания действует с выбранной будущей даты, а не переписывает прошлый знаменатель достижений.

Без расписания: отметка «Сделано сегодня», один факт в день по умолчанию. По желанию взрослого — несколько выполнений с явно заданным лимитом, не бесконечные клики ради звёзд. В MVP оставить один факт в день.

### 3.5 Награды
- Доступный баланс, начислено за период, дата следующего решения.
- Карточки направлений: уроки, прогулки, поручения; условия, факты, результат.
- Дневник кошелька: дата, причина, окно оценки, изменение, баланс после операции.
- AI-объяснение или шаблонный текст с одинаково понятными основаниями.
- При недостатке данных: «Пока знакомимся с твоим ритмом», требования для первой оценки.
- Предварительный расчёт не увеличивает доступный баланс.

### 3.6 Мой мир
**Живой архипелаг**, а не коллекция декоративных предметов. Четыре свободно переключаемых тематических острова: «Тихая бухта» (поселенцы), «Брик-сити» (конструктор), «Куболесье» (кубический мир) и «Банановый залив» (весёлые непоседы). Названия рабочие, графика собственная. Запрошенные LEGO/Minecraft/миньоны служат тематическими ориентирами; брендированные версии и ассеты не входят в текущую поставку.

Выбор миров — горизонтальная прокручиваемая лента панелек с уникальными графическими эмблемами. Коллекция пополняется бесплатно из поискового каталога, число слотов не ограничено. Текущий набор — четыре темы; добавление новых требует ассетов и записи каталога, но не перестройки навигации.

Прогресс каждого мира независим; кошелёк общий. Переключение бесплатно, не сбрасывает улучшения. Анимация автоматически запускается при открытии мира, кнопки движения/паузы нет. При уходе со страницы или переключении мира старая сцена удаляется. При скрытии вкладки — пауза до её возвращения; системное reduced-motion сохраняется. Жизнь — как движения характерных для темы персонажей, так и детали каждого крупного объекта: дым, флаги, вода, листья, птицы, животные, механизмы и свет. Герой главной, эмблемы и карточки улучшений статичны. Открытия меняют постоянное состояние: территория → ресурсы → новые занятия жителей → следующая территория. Никакого голода, разрушения, потери жителей, ресурсов или звёзд за отсутствие. Фоновая симуляция на закрытой странице не нужна: она визуально продолжается при возвращении без начисления валюты.

Четыре тематических этапа: открытие земли (60), мастерская (90), гавань (120), маяк/праздник (180). Покупка последующего этапа требует предыдущего. До покупки доступен бесплатный явно помеченный предпросмотр 0–4; он не меняет кошелёк и прогресс. После покупки сцена перестраивается и объясняет, что изменилось в жизни. В макете покупка выполняется одним нажатием кнопки с явной ценой; production добавляет подтверждение и атомарную серверную транзакцию.

Подробные цепочки и компоненты: [LIVING-WORLDS.md](LIVING-WORLDS.md).

### 3.7 Настройки
- Общие настройки не содержат профиль. Здесь остаются дополнительные занятия/поручения, расписания и настройки интеграций.
- Тема вынесена в header слева от кошелька и аватара: светлая / тёмная / системная, доступна на всех экранах приложения.
- Родительские: занятия, типы целей, расписания, отпуск, подтверждение качества, правила наград, AI-режим и согласие на передачу обезличенных агрегатов.
- Административные: Supabase URL, серверная строка PostgreSQL, необходимые auth-настройки, OpenAI key, имя модели. Поля секретов маскируются, read API возвращает только configured=true/false и допустимые последние символы, не значение.
- Реальная авторизация и административный интерфейс не реализованы в макете. Поля секретов в нём специально заблокированы.

### 3.8 Профиль пользователя
Отдельный экран `#profile`, открываемый кнопкой пользователя в header, не пунктом общих настроек. Только пользовательские данные: имя, аватар, класс, часовой пояс. Редактирование и сохранение. Нет API-ключей, расписаний, наград или редактора поручений.

Кнопка **Sign Out / Выйти**: в макете ставит таймеры на паузу, скрывает приложение и показывает отдельный экран выхода. Повторное открытие вкладки/перезагрузка сохраняет демо-статус выхода через sessionStorage; локальная история не удаляется. Это демонстрация UX, не контроль доступа. В production: серверная инвалидация сессии, удаление auth-cookie и чувствительного кеша, защищённые маршруты; политика таймеров при выходе подтверждается сервером.

### 3.9 Знакомство с программой
Wizard из четырёх шагов: **Замечай время → Расти понемногу → Получай звёзды → Пробуждай жизнь**. Первый показ автоматический, затем ручной запуск на главной, в sidebar и в мире. Доступны Назад, Далее, пропуск и Escape; native dialog удерживает фокус. Завершение/пропуск сохраняется; повторный просмотр не начисляет валюту.

В последнем шаге можно выбрать тему острова и сравнить начальный лагерь, первые улучшения и развитый мир. Это предпросмотр: выбранная тема сохраняется, показанные здания не становятся купленными. Финальный переход показывает фактический остров ребёнка. Отдельно объяснить: качество уроков важнее скорости, награды за устойчивость, мир не страдает без посещений.

## 4. Временная модель и таймеры

### 4.1 Основные сущности
`Activity`: owner, kind=timed|boolean, category=lesson|walk|reading|custom, objective=decrease|reach|maintain|none, target_seconds, active_from, archived_at.
`TimeEntry`: activity, owner, activity_date, duration_seconds, source=timer|manual, quality_status, workload, note, timestamps, revision.
`TimerDraft`: owner+activity (уникально), accumulated_ms, running_since UTC, state, revision.

Продолжительность хранится целым числом секунд, не float-минутами; UI округляет только отображение. В таймере допустимы миллисекунды. События хранятся в UTC, отчётная дата — локальная date с зафиксированным часовым поясом. Переход на летнее время не должен менять фактически прошедшую длительность.

### 4.2 Состояния и команды
`idle → running → paused → running`; `running|paused → save → idle`; `running|paused → reset → idle`.
- Начало/пауза/сброс/сохранение выполняются сервером атомарно с версией и idempotency key.
- Отрисовка через интервал — лишь UI, не источник истины. Сервер считает running_since + накопление.
- Переключение страницы не ставит на паузу и не сбрасывает таймер.
- Таймеры разных занятий полностью независимы. При запуске второго работающего таймера показать предупреждение о пересечении; предложить паузу первого, но не делать её молча.
- Сохранение работающего таймера сначала фиксирует текущую длительность и затем записывает/обнуляет в одной транзакции. При ошибке БД черновик сохраняется.
- Ручная запись не меняет черновик. Дополнительное сохранение за тот же день создаёт новую запись; график показывает сумму.
- Несохранённое время после перезагрузки восстанавливается с сервера; конкурентное управление на двух устройствах приводит к 409 и обновлению состояния, а не двойной записи.
- Пересечение полуночи: спросить дату отнесения; по умолчанию дата начала сессии. В MVP не делить одну сессию автоматически; явно показывать выбранную дату перед сохранением. В макете упрощение: сохранение за текущий день.
- Забытый таймер более 4 часов просит подтверждение; более 24 часов требует исправления. Не обрезать молча.
- Будущая дата запрещена. Ручной ввод 1–1440 минут; сохранение таймера не менее 1 секунды. Проверять суммарные аномалии и пересечения, но не выдавать нравственную оценку ребёнку.
- Редактирование/удаление — с подтверждением и аудитом. Архивирование занятия сохраняет историю.

## 5. Начисления: проверяемая политика v1

Все приведённые коэффициенты — **предлагаемые продуктовые параметры**, а не медицинские или педагогические нормативы. 120 минут прогулки — заданная пользователем цель, корректируемая взрослым.

### 5.1 Окна, регулярность и защита от повторов
Предварительная оценка на локальную дату D использует семь **завершённых** дней `[D−7, D−1]`; база — `[D−14, D−8]`. Сегодня не включать: день ещё не окончен. В интерфейсе показывать точные границы.

Первая финальная оценка после 14 дней наблюдения; далее каждые семь дней по дате активации политики. Финальные текущие окна не пересекаются; сравнительная база может совпадать с предыдущим оценённым окном. Ежедневный просмотр не начисляет звёзды. Уникальный ключ `(child_id, policy_version, award_period_end, category)` исключает повтор. Смена режима или повторная попытка AI не создают вторую оценку того же периода: дополнительно одна финальная запись категории на период независимо от версии.

Дни без данных не считать нулевыми минутами уроков и не использовать как улучшение. Пропуски обязанностей в запланированные дни — невыполнение, если нет заранее подтверждённого исключения. Для прогулок нужен явный статус дня: recorded / no_walk / excluded / missing; при missing оценка остаётся предварительной и взрослому предлагается закрыть данные.

### 5.2 Домашние задания
Для каждого предмета:
1. Не менее 3 сопоставимых подтверждённых учебных дней в каждом из двух окон. Для редких предметов можно отдельно настроить более длинное окно; по умолчанию награда ждёт данных.
2. Сравнивать только выполненную работу сопоставимого объёма и сложности (родитель отмечает обычная/повышенная; исключённая работа остаётся на графике, но не в расчёте).
3. Все обязательные завершения за оцениваемые дни должны быть подтверждены; нельзя выбрать лишь самые быстрые результаты.
4. B — медиана дневного времени базы; C — медиана текущего окна. Прогресс `p=(B−C)/B`; B>0.
5. При p<5% награда 0; от 5% — 10 звёзд, от 10% — 20, от 15% — 30 за предмет. Не более 100 звёзд за все уроки в период. Без прогресса награды за скорость нет.
6. Не поощрять повторное сокращение до нуля: взрослый задаёт разумный индивидуальный нижний порог. При подозрительно коротких результатах нужно подтверждение, не автоматический бонус.

Пример: медиана математики 35 → 30 мин: p≈14,3%, награда 20. 35 → 35: 0. 35 → нет записей: недостаточно данных, не 100% улучшение. Пять предметов по 30 дают лимит 100.

### 5.3 Прогулки
Для включённых дней `r_d=min(minutes_d/120,1)`. E — число включённых дней; не менее 5. `R=mean(r_d)`, K — число дней достижения цели. Нулевой день, подтверждённый как no_walk, входит с нулём; missing блокирует финальную оценку.
- K/E≥5/7: 40 звёзд за регулярное достижение цели, даже если дальше увеличивать время уже не нужно.
- Иначе при росте R относительно базы минимум на 0,10 и R≥0,60, при прогулках минимум в 4 включённых дня: 20 звёзд.
- Иначе 0. Ветки не суммируются; максимум 40 за период.
- При E≠7 использовать `ceil(E*5/7)` для первого порога. При отсутствии достаточной базы возможна награда за устойчивое достижение цели, но не за улучшение относительно неизвестной базы.
- 240 минут не дают двойную награду. Болезнь не порождает штраф и не принуждает гулять.

### 5.4 Запланированные поручения
N — число запланированных экземпляров обязанностей в окне; C — число выполненных. Считать экземпляры, а не количество названий задач. N=0 → нет оценки/награды, не 100%.
- C/N<0,60: 0.
- Иначе `floor(20*C/N) + min(15, floor(C/3))`.
- При C=N дополнительно 5; максимум 40 звёзд за период.
- Для регулярности нужны выполнения минимум в `min(3, число дней с запланированными поручениями)` разных днях. Еженедельное пятничное дело может квалифицироваться, если это единственное запланированное дело.
- Больше выполненных экземпляров при одинаковом проценте увеличивает бонус до лимита. Добавление/дробление задач ребёнком не увеличивает коэффициенты: каталог и значимость утверждает взрослый; одинаковые дубли не допускаются политикой.

Пример: N=10, C=10 → 20+3+5=28. N=10, C=6 → 12+2=14. N=10, C=5 → 0.

### 5.5 Добровольные поручения
Рекомендуемый default — отметки без немедленной валюты, включаемые в отдельное достижение регулярности. Опционально взрослый включает 2 звезды за подтверждённый факт, максимум один в день на дело, не больше 6 в день и 20 за период. Это явное исключение из недельной логики, не часть обязательного процента. Снять/поставить checkbox не позволяет повторно получить награду.

### 5.6 Дополнительные timed-занятия
Чтение: reach 20 минут, минимум 4 дня в неделю → предлагаемые 15 звёзд; objective=none только учитывает время. Универсальные цели задаёт взрослый: target, eligible weekdays, required day count, period reward cap. Новая задача никогда автоматически не наследует вознаграждение за скорость уроков.

### 5.7 Исправления и закрытие периодов
До финализации данные пересчитываются свободно. После — история записей остаётся редактируемой с аудитом, но выплаченная награда не пересоздаётся. Родительская корректировка оформляется отдельной ledger-операцией со ссылкой на причину; автоматического отрицательного баланса и отъёма объектов нет. Поздние записи не должны повторно награждаться в следующем окне. Финальные отчёты содержат snapshot данных и версию политики.

## 6. AI-режим

Два режима: `deterministic` и `ai_assisted`. В первом сервер применяет формулы и шаблон объяснения. Во втором сервер сначала проверяет право на награду и лимиты, затем передаёт обезличенные агрегаты и диапазоны AI. Модель предлагает конкретную сумму в допустимом диапазоне и короткое доброжелательное объяснение; сервер проверяет схему, арифметику, пределы и основания. Для категории уроков отсутствие прогресса всегда задаёт диапазон [0,0].

Предлагаемый диапазон AI — от рассчитанной базовой суммы до +10% с округлением вниз и жёстким лимитом категории. Точный диапазон следует утвердить до разработки. AI не выполняет SQL и не вызывает кошелёк. Названия пользовательских задач — недоверенные данные, не инструкции. Не передавать имя, возраст, email, заметки и подробные даты без необходимости; достаточно обезличенного идентификатора окна и чисел.

Ответ: `schema_version, category_results[{category, amount, reason_code, explanation}], total, encouragement`. Сохранять версию prompt, model, входной snapshot hash и результат для аудита. При таймауте, ошибке валидации, отсутствии ключа — детерминированный fallback, отмеченный в отчёте. Результат финализируется ровно один раз. Пользователь не повторяет запрос ради более выгодной суммы.

Вызовы OpenAI только с backend; ключ хранится в серверном окружении. Это соответствует [официальной документации OpenAI по аутентификации](https://developers.openai.com/api/reference/overview). Модель и её доступность выбираются при реализации, без привязки макета к устаревающему имени модели.

## 10. Auth, RLS и защита данных

Предлагается Supabase Auth с хранением учётных записей в auth-схеме внешнего проекта; application profiles — в public. Backend проверяет сессию и права. Конкретный SDK/механизм верификации токенов и RLS следует сверить с официальной документацией Supabase на этапе реализации.

- Пароли обрабатываются auth-провайдером; приложение не хранит их открытым текстом, не логирует и не реализует собственное шифрование паролей.
- Сессия через Secure, HttpOnly, SameSite cookie; для mutation — защита CSRF. Access/refresh token не хранить в localStorage production-приложения.
- Row Level Security для пользовательских таблиц, политика own/linked-child; DB role backend не должен без необходимости обходить RLS. Если административное соединение обходит её, обязательна отдельная проверка owner на каждом запросе, с тестами, и запрет экспозиции такой роли клиенту.
- Прямой клиентский write в rewards/wallet/world_unlocks запрещён. В production клиент не подключается к БД административным ключом.
- Rate limiting login и AI, закрытые логи, исключение секретов, CORS на свой origin, ограничение размера запросов, HTTPS.
- Экспорт и удаление профиля взрослым, настраиваемое хранение аудита, резервные копии. Детские данные не включать в публичный seed или crash reports.

## 11. .env и настройка установки

Маскирование — только интерфейс, не защита хранения. `.env` содержит секреты открытым текстом на диске, поэтому доступ к нему ограничен runtime-пользователем (0600), файл исключён из Git и Docker image. Рекомендуется persistent bind mount/volume `/data/config/app.env`; runtime читает его явно. Перезапуск контейнера сохраняет конфигурацию. Не рассчитывать, что Docker `env_file` автоматически перечитает изменённый файл.

Административный API:
1. Повторная аутентификация администратора, CSRF, audit без значений.
2. Принимает только allowlist ключей; запрет CR/LF и произвольных имён, безопасная сериализация .env.
3. Проверяет соединение с таймаутом, TLS и ограничением допустимых адресов; не превращать «проверку подключения» в SSRF к внутренним сервисам.
4. Атомарно пишет временный файл + rename, сохраняет права. Read API не возвращает секрет.
5. Пересоздаёт клиент/connection pool или возвращает `restart_required`; при неудаче старое подключение остаётся рабочим.
6. Не позволяет ребёнку или обычному родителю менять БД для всей установки.

Предлагаемые переменные: `APP_ENV`, `APP_BASE_URL`, `SESSION_SECRET`, `DATABASE_URL`, `SUPABASE_URL`, серверные параметры Supabase Auth, `OPENAI_API_KEY`, `OPENAI_MODEL`, `CONFIG_FILE`. `.env.example` содержит только placeholders. Настоящие ключи в макет не вводить.

## 13. Пересоздание БД, seed и публикация

На следующем этапе поставить миграции и **отдельный опасный reset-скрипт**, а не выполнять DROP при старте сервера. Скрипт:
- Требует явные флаги `--reset --confirm-project-ref=<ref>` и отдельный opt-in для production.
- Проверяет целевой host/project и предлагает backup; dry-run по умолчанию.
- Пересоздаёт только принадлежащие приложению объекты в dependency order; не удаляет Supabase managed auth/storage schema.
- Применяет таблицы, функции, ограничения, индексы, RLS/grants и seed транзакционно, где возможно.
- Создание auth-пользователей идёт через поддерживаемый Admin API отдельно; не редактировать auth.users SQL вручную. Полное удаление auth-аккаунтов — отдельная процедура с отдельным подтверждением.
- Seed содержит предметы-шаблоны, каталог мира, политику v1; демо-записи и Алексей — только опциональный dev seed. Предметы конкретного ребёнка создаются при onboarding.

Публикация: README с quickstart, архитектурой и ограничениями; `.gitignore`, `.env.example`, миграции, Dockerfile/compose, lockfiles зависимостей, линтеры/форматтеры, тесты, CI. SECURITY.md и CONTRIBUTING.md до публичного релиза. Лицензию выбрать владельцу; права на логотипы и userpic подтвердить отдельно. Не коммитить реальные пароли, ключи, дампы, логи и персональные записи. Один контейнер запускается непривилегированным пользователем; healthcheck, restart policy, ограничение ресурсов, external DB TLS. TLS termination описывается отдельно от контейнера.

## 14. Критерии приёмки и тесты

### Учёт
- Математика 10 минут → пауза → русский 15 → пауза → математика +5: сохранено 15 и 15, таймеры не смешиваются.
- Перезагрузка/смена страницы не обнуляет draft; два одновременных save создают одну запись.
- Ручная запись за вчера изменяет вчерашний итог, но не draft; будущая дата отклоняется.
- Сохранение при ошибке БД не обнуляет таймер. Два устройства корректно разрешают revision conflict.
- Midnight, timezone, DST, длинная сессия, многократные pause/resume покрыты тестами.

### Поручения и награды
- Будни не создают обязательства в выходные; пятничное — только в пятницу, с учётом timezone.
- Checkbox false→true→false→true не дублирует occurrence, completion или награду.
- N=0, недостаточная база, B=0, missing walk data, отпуск не превращаются в ложные достижения.
- Нет улучшения уроков → 0 по категории независимо от AI-ответа.
- Ежедневные просмотры скользящего окна и повторные jobs не удваивают выплату; смена режима тоже.
- Политика, расписание и прошлые записи после закрытия не переписывают исторический ledger.
- Конкурентные покупки не создают отрицательный баланс; предмет открывается один раз.

### Безопасность
- Пользователь A не читает/меняет записи, таймеры, поручения, награды, покупки B, включая подбор UUID и вызов repository без UI.
- Ребёнок не получает административные endpoints и секреты; ключи не встречаются в bundle, API reads и логах.
- Prompt injection в названии занятия не меняет политику или сумму сверх лимитов.
- Reset не работает без подтверждения нужного проекта; миграции повторяемы.

### Интерфейс
- Проверить 390×844, 844×390, 768×1024, 1024×768, 1440×900; нет горизонтального scroll всей страницы.
- Светлая/тёмная/системная тема, клавиатура, focus, screen reader labels, zoom 200%, reduced motion.
- Пустые/ошибочные/загружающиеся состояния; длинные названия; графики не считают пропуски нулём.
- PNG-артефакты присутствуют, цвета соответствуют палитре.

## 15. Этапы реализации

1. **Сейчас:** макет и согласование правил, компонентной структуры, сценариев.
2. **Основа:** репозиторий, FastAPI/React, Docker, миграции, Supabase Auth, профили и изоляция.
3. **Учёт:** занятия, независимые серверные таймеры, история, графики, поручения и расписания.
4. **Награды и игра:** детерминированная политика, snapshots, ledger, покупки и мир; concurrency tests.
5. **Дополнительно:** AI, административная запись .env, экспорт, улучшенная доступность, подготовка публичного релиза.

До реализации обсудить: способ входа ребёнка без собственного email; степень участия взрослого; допустимость разовых наград; формулы/лимиты; правила сопоставимости домашних заданий; сроки хранения и необходимость offline-режима. Полный offline sync, push-уведомления, социальные функции и сложная игра не входят в MVP.
