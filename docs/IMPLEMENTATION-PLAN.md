# Реализация согласованного MVP

## Граница первой рабочей версии

Основание — `SPECIFICATION.md` и утверждённый макет `prototype/`. Макет сохраняется как визуальный эталон, но его localStorage, демо-вход и демо-баланс не используются в рабочем приложении.

Первая версия: React/TypeScript + FastAPI, внешний Supabase PostgreSQL/Auth, серверные занятия/таймеры/история/поручения, детерминированные периодические награды, кошелёк и покупки улучшений четырёх миров. Фронт и API работают на одном origin и поставляются одним контейнером. Ключи не попадают в браузер.

Согласно этапу 5 спецификации, отдельным этапом остаются AI-оценка, защищённая административная запись `.env`, экспорт/удаление данных и расширенные административные сценарии. Полный offline sync, push и социальная игра вне MVP. Нереализованные функции должны быть обозначены явно, а не имитировать успех.

## Работа команды

- **Claude-инженер backend:** Python-модули, серверный API, Supabase Auth, схема/ограничения, безопасный reset, доменные тесты.
- **Claude-инженер frontend:** React-экраны по утверждённому макету, Unovis, реальные запросы API, обработка загрузки/ошибок, сборка и UI-тесты.
- **Claude-тестировщик:** независимые негативные проверки, контрактная совместимость, регрессии и отчёт `MVP-QA.md`.
- **Основная сессия:** интеграция, Docker/CI, проверка результатов и эксплуатационная документация.

Контракт обмена — `API.md`. Доработки контрактов синхронизируются между инженерами. Исходный макет не изменяется в рамках этой реализации.

## Проверка перед использованием реальных данных

1. Автоматические backend-тесты и frontend typecheck/build.
2. Независимые тесты таймеров, изоляции, расписаний, наград и покупок.
3. Проверка браузера на синтетических данных; проверка доступности собранной страницы.
4. Применение схемы в отдельном Supabase-проекте и проверка реального login/refresh/logout, RLS, двух пользователей и конкурентных транзакций.
5. Docker-сборка и smoke test; HTTPS, cookie policy, резервное копирование.

Пункты, для которых нет окружения/учётных данных, фиксируются как **не проверенные**, а не пройденные. Рабочие ключи вводятся только локально на сервере установки; их не требуется присылать в чат.
