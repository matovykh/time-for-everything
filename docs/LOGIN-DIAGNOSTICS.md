# Диагностика зависающего входа (`login_stage`)

Короткая инструкция для **диагностической сборки**: при входе (`POST /api/v1/auth/login`) приложение пишет
в лог строки с меткой `login_stage` в начале и в конце каждого этапа. Сборка **ничего не исправляет** — в том числе
таймауты базы данных. Она только показывает, **на каком этапе** вход теряет время или падает.

---

## 1. Сборка и установка — как обычное обновление

Собирайте и ставьте строго по [NAS-UPDATE.md](NAS-UPDATE.md) (быстрый путь, шаги 1–9). Для этой сборки:

- **Новых настроек нет.** `app.env` не меняется, `DB_*` не трогаем.
- **Миграций нет.** Шаг 3 должен показать `schema_version=20261006000002`; другое значение — стоп.
- Откат — как обычно (раздел 8 NAS-UPDATE): вернуть прежний `TFE_IMAGE`.

**Коммит этой сборки — ровно пять файлов** (вместо списка из раздела 1.4 NAS-UPDATE):

```sh
git -C "$APP" add -- \
  backend/app/core/login_stages.py \
  backend/app/db/session.py \
  backend/app/modules/accounts/router.py \
  backend/tests/test_login_diagnostics.py \
  docs/LOGIN-DIAGNOSTICS.md
git -C "$APP" diff --cached --stat
```

В `--cached` должны быть только эти пять файлов. Остальные ваши незакоммиченные изменения документации
сюда не добавляйте. Перед коммитом и push — проверка на секреты из раздела 1.2 NAS-UPDATE.

## 2. Что пишется в лог

Одна попытка входа = один `request_id`. Если сервер успел ответить, этот код можно найти
в заголовке ответа `X-Request-ID` или поле `request_id` JSON-ошибки в панели «Сеть».
Форма входа не обязана показывать его на экране. Логгер — `app.auth.login`.

Строки выглядят так (начало — дата, время, уровень, логгер):

```text
… INFO app.auth.login login_stage request_id=<код> stage=<этап> event=start
… INFO app.auth.login login_stage request_id=<код> stage=<этап> event=ok elapsed_ms=<мс>
… WARNING app.auth.login login_stage request_id=<код> stage=<этап> event=error outcome=<raised|swallowed> elapsed_ms=<мс> error=<класс> …
```

- `event=start` — этап начался; `event=ok` — закончился успешно; `event=error` — закончился ошибкой.
- `elapsed_ms` — сколько длился **этот этап**, в миллисекундах.
- `outcome=raised` — ошибка прервала вход. `outcome=swallowed` — ошибка записана, но вход продолжился.
- После `error=` могут идти `status=`, `code=` (код ответа), `cause=` (класс исходной ошибки) и для ошибок
  базы `category=`, `driver_error=`, `sqlstate=`.

Этапы по порядку:

| `stage` | Что происходит | Если застряло здесь |
|---|---|---|
| `db_dependency` | Сессия базы для запроса. Выполняется **до** остальных этапов. Проверка схемы кэшируется: после первой успешной проверки схемы этап обычно **базу не трогает**; после неудачной проверки следующая попытка проверяет её снова | Первое подключение к БД |
| `supabase_sign_in` | Проверка email и пароля в Supabase Auth | Сеть/TLS до Supabase Auth |
| `jwt_verify` | Проверка подписи полученного токена | В том числе загрузка ключей JWKS из Supabase, если их ещё нет в кэше |
| `ensure_profile` | Чтение/создание профиля — обычно **первый настоящий запрос к БД** | Соединение/запрос к БД |
| `reward_evaluation` | Проверка наград за период. Ошибка здесь вход **не блокирует** (`outcome=swallowed`) | БД; длительное ожидание может превысить таймаут браузера |
| `response` | Сбор ответа и cookies. **Тоже может обращаться к БД**: после отката на этапе наград данные профиля подгружаются заново, а для взрослого читается список детей | БД |

**Секретов в этих строках нет:** ни email, ни пароля, ни токенов, ни cookies, ни текста ошибок, ни SQL.
Если вы увидели что-то из этого — не пересылайте лог и сообщите об ошибке. Остальные строки лога перед
отправкой тоже просмотрите.

## 3. Как воспроизводить — одна попытка, без повторов

1. Сделайте **одну** попытку входа тестовым аккаунтом и дождитесь результата: успех, ошибка или
   сообщение о таймауте (браузер ждёт вход **20 секунд**).
2. Если появился «Код запроса» — запишите его. Запишите и время попытки.
3. Посмотрите лог (раздел 4). Повторять — **не раньше чем через минуту**, всего не больше 2–3 раз.

Не нажимайте «Войти» много раз подряд: это лишние запросы к Supabase и базе, срабатывает лимит попыток
(`429`), а строки разных попыток перемешиваются.

**Таймаут или закрытая вкладка в браузере не останавливают сервер.** Браузер через 20 секунд перестаёт
ждать (и «Кода запроса» тогда нет), но сервер продолжает этот вход. Поэтому `event=ok` или `event=error`
может появиться в логе **позже**, чем браузер сдался.

## 4. Команды на NAS

Сначала задайте функцию `tfe` из начала раздела 4 [NAS-UPDATE.md](NAS-UPDATE.md#4-подготовить-nas-снимок-текущего-состояния-и-загрузка-образа).
Команды только читают лог.

```sh
CID=$(tfe ps -q app)

# Все строки входа за последние 10 минут
sudo docker logs --since 10m "$CID" 2>&1 | grep -F 'login_stage'

# Одна попытка — по «Коду запроса»
RID='ВСТАВЬТЕ_REQUEST_ID'
sudo docker logs --since 10m "$CID" 2>&1 | grep -F "request_id=$RID"
```

Если «Кода запроса» нет (таймаут в браузере), найдите `request_id` в первом выводе по времени попытки
и выполните вторую команду с ним. Вторая команда покажет и другие строки этой попытки, например
`database unavailable method=POST route=/api/v1/auth/login category=…` или
`reward evaluation at login failed`.

## 5. Как читать результат

Смотрите строки **одного** `request_id` по порядку.

| Что видно | Вывод |
|---|---|
| Последняя строка — `event=start` какого-то этапа, после неё нет `ok`/`error` | Вход висит на этом этапе. Подождите 2–3 минуты и посмотрите снова: если `ok`/`error` так и нет — это место зависания |
| `event=error outcome=raised` | Этап упал и прервал вход; браузер получит ошибку, только если ещё не прекратил ожидание. Смотрите `error=`, `code=`, `category=` |
| `stage=supabase_sign_in event=error error=InvalidCredentials` | Неверный email или пароль — это не сбой |
| `stage=reward_evaluation event=error outcome=swallowed` | Так и задумано: награды вход не блокируют. Дальше должен идти этап `response` |
| Все этапы `event=ok`, а браузер показал таймаут | Обработка этапов завершена. Сравните их длительность с 20 с; это ещё не доказывает доставку ответа браузеру |
| `db_dependency event=ok` и дальше ничего, ответ `429` | Сработал лимит попыток входа (проверяется до Supabase, отдельного этапа нет) |
| `event=start` без конца, а следом `Application startup complete` | Контейнер перезапустился посреди входа — это не зависание этапа; проверьте `tfe ps` |
| Строк `login_stage` нет совсем | Запрос до входа не дошёл: работает старый образ (проверка — раздел 7.1 NAS-UPDATE), сеть, или ошибка `403 csrf_failed` (проверяется раньше входа) |

Для разбора пришлите: строки с этим `request_id`, время попытки, текст ошибки в браузере и «Код запроса».

---

## 6. Чего эта сборка не делает

- **Не исправляет** таймауты и зависания БД или Supabase и не меняет никакие таймауты — только пишет лог.
- Не добавляет настроек и миграций, не трогает `app.env` и данные.
